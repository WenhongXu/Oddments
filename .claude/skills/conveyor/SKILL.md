# Conveyor —— 批量循环任务处理（逐项推进法）

> 取名 Conveyor（传送带）：同构的循环项像流水线上的工件，依次通过同一道标准工序，
> 一次只加工一件，件件有编号、有工单、有质检记录。

## 这个 skill 解决什么问题

你（智能体）所在的平台通常无法编写真正的程序循环来批量调用模型，只能靠你自己
一项一项地推进。逐项推进最常见的事故是：乱序、漏项、重复做、做到一半忘了做到哪、
把 A 客户的数据算到 B 客户头上、结果堆在一起分不清谁是谁。

本 skill 用两件事消除这些事故：

1. **文件化状态**——计划、进度、异常全部落在文件里，随时可中断可恢复，不依赖对话记忆；
2. **单项回合制**——每次只处理一个循环项，做完一个、登记一个、再开下一个。

> 术语约定：被重复处理的对象统称"**循环项**"（可能是客户、合同、门店、工单……）。

---

## 五条铁律（任何阶段都不得违反）

1. **一次只处理一个循环项。** 当前项未到终态（已完成/已跳过/部分完成），不碰下一项。
2. **做完一项立刻更新清单，再开下一项。** 禁止连做几项后补记，禁止凭印象批量改状态。
3. **状态只信文件，不信记忆。** 对话上下文可能被压缩或截断；每个回合开始都重新读清单。
4. **循环项之间严格隔离。** 处理第 N 项时只读第 N 项的输入，不把上一项的数据、结论、
   猜测带进当前项。
5. **交付物必须可识别。** 一切以 ID 归档：目录名带 ID、文件头写 ID、清单里对得上号。

---

## 流程总览

```
阶段 0 理解任务（不懂就问）
  → 阶段 1 试跑第一项（趟通流程，固化 SOP）
  → 阶段 2 建立清单与工作区
  → 阶段 3 逐项循环（单项回合制 + 异常三级决策）
  → 阶段 4 完整性核对、汇总报告与打包交付（zip）
```

> 阶段 1 与阶段 2 的顺序可以互换：如果不先枚举清单就找不到样例项，就先建清单再试跑，
> 试跑项即清单中第 1 项。

## 阶段 0 — 理解任务

从用户的提示词中提取以下要素。要素分两类：**必问要素**缺了不能开工，
用户没说就必须问；**可默认要素**用户没说就按默认值执行，但要写进计划并告知用户。

### 必问要素（缺一个都不能开工，用户没说就问）

| 要素 | 要弄清什么 | 示例 |
|------|-----------|------|
| 循环项 | 重复处理的对象是什么 | 客户、合同、门店 |
| 清单来源 | 循环项的完整列表从哪来；数据放在哪里 | 目录扫描 / 清单文件 / 用户口述 / 系统查询 |
| 每项输入 | 每个循环项有哪些输入（文件、数据）、命名规律、**阅读与处理的先后顺序** | 先读基本信息，再读交易流水 |
| 处理流程 | 对一个循环项要执行哪些步骤（分析、改写、生成、核对、写回系统……本 skill 不限定动作类型）；判断标准是什么 | 分析风险点并按规则打 1~5 分 |
| 交付物 | 每项必须产出什么：文件名、格式、必备内容、验收标准 | `<ID>_分析报告.md`，须含评分和依据 |

> 交付物的例外：用户没说时，可以**提出具体方案请用户确认**（可与试跑成果一起确认），
> 但不能不定义就开工——**交付物定义是阶段 4 逐项核对的前提**。

### 可默认要素（用户没说就按默认，写入计划并在首次汇报时告知）

| 要素 | 要弄清什么 | 默认值 |
|------|-----------|--------|
| ID | 如何唯一识别一个循环项。**字段名不一定叫"ID"**，可能叫客户号、编号、社会信用代码、工单号 | 从数据中找唯一字段；实在没有就用"序号_名称"构造（如 `007_张三公司`），写入清单固定下来，全程使用 |
| 顺序与范围 | 是否要求特定处理顺序；全量还是子集 | 清单自然顺序，全量 |
| 输出位置 | 工作区根目录放在哪 | 在输入数据旁新建 `<任务名>_结果/` |
| 成果打包 | 是否打包为 zip、打包范围 | 打包：`交付/` + 汇总报告 |
| 异常边界 | 哪些异常可自行处理、哪些应跳过、哪些必须停下来问 | 按阶段 3 的"异常三级决策" |
| 汇报节奏 | 多久向用户报一次进度 | 每完成 1 项报一行；项数很多（>50）改为每 5~10 项一报 |
| 推进模式 | 连续自动推进，还是每完成一项等用户确认后再继续 | 连续推进；用户要求时切换为"逐项确认" |

### 提问规则

- **先问后动**：必问要素有缺失时不得开工。一次问齐所有缺失项，不要挤牙膏式追问；
  用户已经说清楚的不要重复问。
- **带默认值提问**：每个问题都附上你建议的答案，让用户可以一句"都按你建议的"快速通过。
- **可默认要素不问也行**：直接按默认执行，但必须写入 `01_任务计划.md` 并在首次汇报时
  列出，给用户纠正的机会；若正好要提问，可顺带一并确认。
- **自动化场景**（无法与用户交互）：必问要素若能从数据中高置信推断 → 采用，并在计划
  与汇总报告中显著标注"推断，未经确认"；推断不出 → 停止并向用户说明缺什么，
  **不要瞎猜开工**。
- 用户说"你看着办" → 自己拟定全部要素，写入任务计划，并在第一次汇报时展示给用户。
- 阶段 0 结束时，把全部要素写入 `_批量控制/01_任务计划.md`（草稿），并给每个要素标注
  来源：**用户指定 / 默认 / 推断**。不要只留在对话里。

## 阶段 1 — 试跑第一项（趟通流程）

1. 先按"阶段 2 的工作区结构"创建工作区骨架（`_批量控制/` 与 `交付/`）。
2. 选第一个循环项（或用户指定的样例项），严格按阶段 0 的理解完整走一遍，产出交付物。
3. 过程中把**实际执行的每一步**记下来：读了哪些文件、按什么顺序、做了什么判断、
   产出了什么——整理成《单项标准流程（SOP）》。
4. 把试跑交付物 + SOP 摘要展示给用户，请其确认或修正：
   - 用户提出修改 → 修正 SOP，必要时重做样例项，直到确认；
   - 无法与用户交互（自动化场景）→ 按阶段 0 的交付物验收标准自检，通过后继续，
     并在汇总报告中注明"流程基于首项自校验，未经人工确认"。
5. 确认后，把任务定义 + SOP 定稿写入 `_批量控制/01_任务计划.md`。
   **之后所有循环项严格按 SOP 执行，不再即兴发挥。**

SOP 中途修改规则：循环过程中若发现 SOP 有系统性问题（对多数项不适用），属于
"必须暂停询问"级异常——停止循环，修订计划文件并记录版本，与用户确认已完成项
是否需要返工，然后再继续。

## 阶段 2 — 建立清单与工作区

### 工作区结构（文件方式，首选）

```
<工作区根目录>/
├── _批量控制/
│   ├── 01_任务计划.md      # 任务定义 + SOP（阶段 0/1 的成果）
│   ├── 02_状态清单.md      # 唯一的进度事实来源
│   ├── 03_异常记录.md      # 所有不同构情况，无论是否处理过
│   └── 04_汇总报告.md      # 阶段 4 生成
└── 交付/
    ├── C0012_张三公司/     # 每个循环项一个独立目录：<ID>_<短名>
    │   └── C0012_分析报告.md
    └── C0013_李四商贸/
        └── ...
```

> 目录名可按平台习惯换成英文（如 `_control/`、`deliverables/`），含义与分区规则不变。
> 四个控制文件的完整模板见 [references/templates.md](references/templates.md)。

### 建清单步骤

1. 按清单来源枚举**全部**循环项（扫描目录 / 读清单文件 / 记录用户口述）。
2. 每项一行写入 `02_状态清单.md`，列：`序号 | ID | 名称 | 输入位置 | 状态 | 完成时间 | 备注`。
   状态取值：`待处理` `处理中` `已完成` `已跳过` `部分完成`。
3. **校验 ID 唯一性**：发现重复 ID → 停下来问用户，不要自行猜测归并。
4. 目录名安全化：ID 和短名中去掉 `/ \ : * ? " < > |` 及首尾空格；
   若两个项安全化后冲突，追加 `-2`、`-3` 后缀，并把映射写进清单备注列。
5. 清单建完向用户报告：共 N 项、前 3 项预览、样例项是谁，确认范围无误；
   枚举数量与用户预期不符（如用户说 58 个、实际只找到 55 个）→ 先对齐清楚再开工。
6. 已试跑完成的样例项，状态直接标 `已完成`。

## 阶段 3 — 逐项循环执行

**每个循环项执行同一个"单项回合"，回合之间不重叠：**

### 单项回合（9 步）

1. **取项**：重新打开 `02_状态清单.md`（不要凭记忆），找到第一个 `待处理` 的项，
   将其标为 `处理中` 并保存文件。
2. **对照输入**：列出该项的实际输入（如列出其目录内容），与计划中的预期结构对照。
3. **同构 → 按 SOP 处理**：严格按 `01_任务计划.md` 的 SOP，按规定顺序读文件、执行步骤。
4. **不同构 → 走"异常三级决策"**（见下节）。
5. **写交付物**：写入 `交付/<ID>_<短名>/`；每个交付物文件的开头写元信息
   （循环项 ID、名称、输入来源、SOP 版本、生成时间——模板见 references/templates.md）。
6. **自检**：交付物齐全吗？文件头 ID 与目录 ID、清单 ID 三者一致吗？
   内容确实只来自本项的输入吗？
7. **更新清单**：状态改为 `已完成`（或 `已跳过` / `部分完成`），填完成时间与备注，保存。
8. **汇报一行**：`[N/总数] <ID> <名称> 已完成`；有异常加一句说明。不要长篇大论。
   逐项确认模式下：汇报后等用户确认，再进入下一项。
9. **收尾**：清空对本项细节的依赖，回到第 1 步。下一项的一切以文件为准。

### 异常三级决策（不同构信息的处理）

| 级别 | 典型情形 | 动作 |
|------|---------|------|
| ① 可自行处理 | 文件名不合命名规律但能确认归属；多出一份补充材料；格式略有差异但关键字段都在 | 处理之，交付物照常产出 |
| ② 应跳过 / 部分完成 | 关键输入缺失；文件损坏打不开；内容与该 ID 明显不符（疑似张冠李戴）；无法确认归属 | 该项标 `已跳过` 或 `部分完成`，不硬做 |
| ③ 必须暂停询问 | 清单本身有错（重复 ID、大量漏项）；SOP 对多数项不适用；涉及删除或覆盖已有数据 | 停止循环，向用户说明，等待指示 |

**无论哪一级，都必须当场追加一条到 `03_异常记录.md`**：时间、循环项 ID、发现的情况、
采取的动作、级别、对结果的影响。悄悄处理不记录 = 违规。
拿不准算哪一级时，就近升一级——宁可跳过或询问，不可硬做污染结果。

### 防串扰规则（隔离）

- 处理第 N 项时，只读第 N 项的输入，不顺手打开其他项的文件。
- 不把上一项的数字、结论、猜测带入当前项；每一项都从 SOP 出发独立判断。
- 上下文已经很长时，每个回合开始前重读 `01_任务计划.md` 的 SOP 段落。
- 需要跨项对比、排名、汇总的需求，放到阶段 4 基于各项交付物做，**不在循环中做**。

### 断点续跑

任何时候中断（会话重开、上下文被压缩、平台重启），恢复动作固定为：

1. 读 `01_任务计划.md`，恢复任务定义与 SOP；
2. 读 `02_状态清单.md`，恢复进度；
3. 状态为 `处理中` 的项，其交付目录可能是半成品——**默认清掉该项交付物重做**，
   并在异常记录中注明"中断重做"；
4. 从第一个 `待处理` 项继续单项回合。

### 防漂移抽检（长循环的质量保障）

连续处理大量循环项时，输出质量会不知不觉走样：章节变少、分析变浅、格式跑偏。
对策：

- 每完成 10 项（或总项数的 1/5，取较小者），随机回看 1 项已完成的交付物，
  逐条对照交付物验收标准与 SOP；
- 发现走样 → 记入异常记录并修复该项；若走样从某一项起成片出现，
  按"③暂停询问"处理，与用户确认返工范围。

### 循环中用户插话怎么办

- 与当前项无关的插话（问进度、问细节）→ 先答复，答完继续当前回合，不弃项。
- **"暂停"** → 尽量把当前项做到终态；来不及则清空该项交付目录、状态回退为
  `待处理`（备注"用户暂停回退"），保存清单后停下，汇报停在哪、如何继续。
- **"先做某某项"** → 当前项收尾后调整清单顺序（备注原因），按新顺序取项。
- **"跳过某某项"** → 该项标 `已跳过`，备注"用户要求"，照记异常记录。
- **要求改处理方式** → 走阶段 1 的"SOP 中途修改规则"：改计划、评估已完成项
  是否返工、再继续。

## 阶段 4 — 完整性核对、汇总与打包

1. 确认清单每一行都已到达终态（已完成 / 已跳过 / 部分完成），才进入本阶段。
2. **逐行完整性核查**：`已完成` 的项，其交付目录存在、交付物齐全、文件头 ID 与清单一致；
   发现缺漏 → 将该项改回 `待处理` 重做。
3. 生成 `04_汇总报告.md`，包含：
   - 总数 / 已完成 / 已跳过 / 部分完成 的统计；
   - 异常记录摘要（每条一行，注明处理方式）；
   - **交付物索引**：ID → 名称 → 状态 → 交付路径，一项一行全量列出；
   - 打包信息（zip 文件名、大小、包含范围）；
   - 若流程未经人工确认，明确注明。
4. **打包交付（zip）**——除非用户明确说不需要：
   - 范围：默认打包 `交付/` 整个目录 + `04_汇总报告.md`；用户需要留档审计时，
     可连 `_批量控制/` 一起打包。
   - 命名：`<任务名>_交付_<YYYYMMDD>.zip`，存放在工作区根目录旁。
   - 打包时**保留目录结构**（每个 ID 一个目录），解压后仍能按 ID 识别归属。
   - **页面类交付物（HTML 等）**：打包前确认页面引用的图片、样式等资源都放在
     该项自己的目录内、且用**相对路径**引用，保证解压后直接打开可用；
     若交付物是无法装进 zip 的在线页面 / 链接，在该项目录放一个 `<ID>_链接.md`
     记录 URL 与说明，并在汇总报告索引中标注"链接类"。
   - 工具按平台选用：`zip -r`（Linux / macOS）、PowerShell `Compress-Archive`
     （Windows）、Python `shutil.make_archive`；平台没有打包能力 → 跳过此步，
     在汇总报告中注明"未打包"。
   - 打包后校验：zip 文件存在、大小 > 0；能列出内容时，核对条目覆盖清单中
     所有已完成项。
5. 向用户交付：汇总报告位置 + zip 包位置 + 工作区结构说明 + 待人工跟进事项
   （被跳过的项、待确认的异常）。

## 收尾之后：单项重做与新项追加

收尾不等于永远结束，常见两种后续，都不需要推倒重来：

**单项重做**（如被跳过的项补齐了材料，或用户对某项结果提出修改）：

1. 在清单中找到该行，状态改回 `待处理`，备注重做原因与日期；
2. 清空该项交付目录，按单项回合重做；
3. 重新生成汇总报告、重新打包（zip 用新日期或加 `_v2`），旧包注明作废。

**新项追加**（清单之外来了新循环项）：

1. 先追加进清单：新序号、标注来源与追加日期，校验 ID 不与已有项冲突；
2. 按单项回合处理；
3. 同上更新汇总与打包。

两种情况都**不触碰其他已完成项的交付物**；更新后的汇总报告注明"增量更新：
重做/追加了哪些项"。

## 通用性：输入 / 输出的其他形态

文件方式最稳定，**优先使用**。平台或任务形态不同时按下表适配，
但五条铁律与"单项回合制"不变：

| 环节 | 首选（文件方式） | 其他形态的适配 |
|------|----------------|---------------|
| 清单来源 | 目录扫描、清单文件（csv / xlsx / md） | 用户在消息里给的列表 → 原样落成清单文件；数据库 / API / 连接器查询 → 查询结果落成清单文件；用户逐项提供 → 清单文件逐项追加，来源标"用户提供" |
| 每项输入 | 该项的文件或子目录 | 工具查询结果、网页内容、用户当场粘贴的内容 → **先原文保存**到该项交付目录下的 `输入快照_*` 文件再处理（保证可追溯、可重做） |
| 交付物 | 每项独立目录中的文件 | 页面（HTML）交付 → 页面与其引用的资源放在该项目录内、相对路径引用，随阶段 4 一起打包；需要汇总大表 → 仍先逐项落地，阶段 4 再合并成大表；需要写回外部系统（API / 连接器）→ 写回后在该项目录留一份副本与写回凭证 |
| 状态清单 | `02_状态清单.md` | 平台没有文件系统时的降级方案：**每次回复末尾附上完整清单快照**（格式见 templates.md），下一轮从最近的快照恢复；此法可靠性较低，须主动告知用户风险 |

补充：

- 平台若有待办 / 任务列表工具，可用来辅助提醒，但**文件清单始终是唯一事实来源**
  （文件可跨会话存活）。
- 平台若支持并行或子代理，除非用户明确要求并行，**默认仍然串行逐项**，
  以保证隔离性与可恢复性。

## 大批量与跨会话作业

项数很多（如 > 30）或单项处理很重时：

- **分批推进**：与用户约定每批数量（如 10 项）；每批结束输出一次小结
  （本批完成情况 + 累计进度 + 异常数），确认后继续下一批。
- **上下文卫生**：回合结束后不要把该项的原始数据全文留在回复里，汇报只给一行结论；
  之后需要引用某项细节时，去读它的交付物文件，而不是翻对话记录。
- **跨会话接力**：一个会话做不完就正常收尾，下个会话按"断点续跑"三步恢复。
  这正是一切状态都落文件的原因——新会话不需要旧对话也能无缝接上。
- 感觉上下文已经很长、开始"记不清"时，**主动**按断点续跑流程重读计划与清单，
  不要硬凭印象继续。

## 平台循环检测与前进保证

有些平台内置"循环 / 重复检测"，会在智能体看似原地打转时强制中断。批量任务
天然带重复性，应对思路**不是绕过检测，而是让真实进展可见、并保证自己确实
没有在原地打转**——检测器防的是死循环，你只要不是死循环：

- **每回合必有状态前进**：一个回合结束，清单必须恰好有一行发生状态变化。
  发现连续两个回合清单没有任何变化 → 自己先停下来检查原因，不要等平台出手。
- **自我熔断**：同一项重试累计 2 次仍失败 → 停止重试，标 `已跳过` 并记异常；
  同一个动作（读同一文件、跑同一命令）连续失败也一样，绝不无限重复。
- **汇报差异化**：进度汇报天然带着不同的序号与 ID（`[7/58] C0019 …`）；
  不要输出与上一回合一字不差的内容，更不要空发"处理中……"而无实际动作。
- **分批 + 交互间隔**：项数多时按批推进（见上一节），每批末尾向用户小结一次；
  多数平台对"连续自主执行"的计数会被用户交互重置，最稳妥的是"逐项确认"模式。
- **被中断不是灾难**：若仍被平台强制中断，按"断点续跑"恢复即可，最多损失
  当前一项——这正是本 skill 坚持把一切状态落盘的原因之一。
- **不要伪装**：不要靠输出无意义的变化内容去"骗过"检测器。真实进展、
  批间交互、分会话接力已是正当且最有效的办法。

## 反模式（发现自己正在做这些，立刻停下来纠正）

- 一口气读入所有循环项的数据，"先总体看看"。
- 连做三五项之后才回头补清单状态。
- 把所有项的交付物写进同一个大文件。
- 用名称而不用 ID 命名目录——重名会互相覆盖。
- 遇到归属不明的文件，猜一个归属继续做，而且不写异常记录。
- 清单之外冒出来的新项直接处理。正确做法：先加入清单（备注来源），再按回合处理。
- 处理第 8 项时，凭"第 3 项好像也是这样"的印象下结论。

## 其他注意事项

- **敏感信息**：客户资料常含敏感字段（证件号、账号、联系方式等）。交付物只保留
  任务需要的字段；用户要求脱敏时，把脱敏规则写进 SOP 全程统一；对话汇报中
  不要贴敏感原文。
- **偶发失败先重试**：读文件、调工具偶发报错时，先重试 1~2 次再按异常定级，
  避免把一次网络抖动当成"文件损坏"记录在案。
- **小批量可精简**：项数 ≤ 3 时，四个控制文件可合并为一个（计划 + 清单 + 异常合写），
  但五条铁律、ID 归档、交付物定义先行这几点不变。
- **时间戳统一**：清单、异常记录、汇总报告使用同一种时间格式（建议含日期
  `MM-DD HH:mm`），便于事后对账。
